# Rule: JT1078

Derived from `docs/business/RAAD_Phase3.5_JT1078_Technical_Design_v1.md`.

**Status (ADR-0009, ADR-0024, ADR-0025, ADR-0026):** the procured hardware (`LSZ-C5804DG-Q-F`) is
confirmed JT/T 1078-2016 compliant (ADR-0025, 2026-08-10, superseding ADR-0009's original
non-compliance finding for this hardware). Rule #3's "JT808 command downlink" is literal, not
illustrative: `0x9101`/`0x9102`/`0x9201`/`0x9202`/`0x9205` are standard JT/T 808-enveloped
messages, forwarded by `device-gateway`'s `vendors/jt808/` adapter on the connection it already
holds — no vendor-specific opcode translation, **implemented 2026-08-11** (`commands/
video_signaling.py` + `commands/redis_video_signaling_consumer.py`).

**`services/jt1078/` is a real, tested relay (2026-08-11), not the empty scaffold this status
paragraph originally described** — JT/T 1078 extended-RTP ingest + subpackage reassembly
(spec-verified), session lifecycle, signed single-use viewer tokens, FLV repackaging (including a
real SPS/PPS-aware `AVCDecoderConfigurationRecord` sequence-header path, `FlvMuxer.
feed_annex_b_video`, closing the seam `build_avc_sequence_header_tag` originally left
unpopulated), and a hand-rolled WS-FLV viewer server, all unit/integration-tested over real
loopback sockets with synthetic frames, never against the physical MDVR. Rules #1 (narrowed,
below)/#2/#3/#5 are implemented as described. **Rule #4's concurrency ceiling is now implemented
(2026-08-12, ADR-0026 §8)**: `SessionManager` enforces a configurable global ceiling (default
`50`, citing Phase 2 §13.1's own "e.g., start 50 global") and an independent, configurable
per-organization ceiling (`JT1078_RELAY_MAX_GLOBAL_SESSIONS`/
`JT1078_RELAY_MAX_SESSIONS_PER_ORGANIZATION`), rejecting `create_session` with
`SessionCapacityExceededError` before any session is allocated. **Rule #6's audit requirement is
implemented (2026-08-12)** for session-level open/close: the relay's own session-lifecycle events
are now consumed back into `VideoSession` (see below), and every `VideoSession` transition
(`Requested`/`Started`/`Ended`/`Failed`, each carrying `device_id`/`camera_id`/`actor_id`) already
flows through the shared `audit_entries` write architecture (ADR-0007) automatically — no new
audit code was needed, only closing the reconciliation gap that used to leave `Started`/`Ended`/
`Failed` under-triggered. Viewer-level join/leave granularity is not separately audited — a real,
narrower remaining gap, not silently claimed closed.

**Business API `VideoProviderPort` → relay wiring is real (2026-08-12)** — closes the
"no Business-API-facing control endpoint" gap this status paragraph and `services/jt1078/
README.md`'s own "Explicitly not built this phase" list both previously named.
`backend/raad/modules/video/infra/adapters.Jt1078RelayAdapter` calls a new
`Jt1078RelayRpcClient` (`backend/raad/modules/video/infra/jt1078_relay_client.py`) — a Redis
list-based BLPOP/RPUSH RPC (`raad:jt1078:session_requests` /
`raad:jt1078:session_responses:{request_id}`) — answered by a new `SessionRequestServer`
(`services/jt1078/src/session/session_request_server.py`), then publishes
`Jt1078SignalCommandRequested` on the **existing** broker stream exactly as ADR-0024 §8 already
specifies for device-gateway. **This RPC channel is new and additive, not a replacement for
ADR-0024 §8's mechanism**: device-gateway ↔ relay coordination stays broker-only, unchanged; the
RPC exists solely for the backend ↔ relay session-request/response shape, which the broker's
fan-out Stream model doesn't fit. Full flow: `VideoApplicationService` → `Jt1078RelayAdapter` →
RPC → `SessionRequestServer` (allocates ingest coordinates, mints the viewer token) → broker event
→ device-gateway's `RedisVideoSignalingConsumer` (already built) → real `0x9101`/`0x9201` on the
device's connection.

**One disclosed, deliberate refinement of ADR-0024 §5 point 2's literal wording, now formalized
(ADR-0026 §6, amending ADR-0024 in place)**: that section reads "a... signed viewer token minted
by the backend at session-creation time." In the implementation, the **relay** mints the token —
the backend never holds `JT1078_RELAY_VIEWER_TOKEN_SECRET` (relay-only config, by design, so a
compromised backend process still can't forge a token for a session it never legitimately
brokered). The security property ADR-0024 §5 actually protects — no session-authorization
decision happens outside the backend's own D5/RBAC/(now) per-parent-permission check, which runs
before the RPC call is ever made — is unchanged; only which process computes the token's bytes
differs from the section's literal phrasing.

**The relay-lifecycle reconciliation gap is closed (2026-08-12, ADR-0026 §7).**
`backend/raad/modules/video/events/subscribers.py` now consumes the relay's own
`VideoSessionActivated`/`Ended`/`Failed` events and calls `VideoSession.activate`/`end`/`fail`
through a fresh `VideoUnitOfWork` — `VideoApplicationService.request_live_video`/
`request_playback_video`'s previous eager, optimistic `activate()` call (right after the
provider RPC returned, before the relay had any real signal media was flowing) is removed;
`status` now reflects the relay's own observed reality, with a short, expected async delay
rather than a synchronous lie. **Not closed by this**: ADR-0024 §16's own "defensive
reconciliation timeout" for a `VideoSession` stuck in `REQUESTED`/`ACTIVE` with **no** lifecycle
event ever arriving at all (e.g., the relay process crashed) — that needs a new scheduled job,
out of ADR-0026's own scope, disclosed not silently assumed done.

1. **Parents have zero reachable path to video, anywhere, ever, by default — and only ever
   through an explicit, individually granted, server-enforced permission, never a role-wide
   grant or a client-side toggle (ADR-0026, narrowing this rule 2026-08-12).** The default
   (GPS + notifications only) is unchanged for every parent; `has_video_live_access`/
   `has_video_playback_access` (`transport_ops.Parent`, off by default, org_admin-grantable
   only) are the sole exception, and the full authorization chain (self identity → explicit
   permission → child/device ownership) is still enforced entirely in the Business API
   (`interfaces/http/policy_guards.resolve_d5_decision`) before any signaling reaches this
   service — this service itself performs no authorization of its own either way, unchanged.
   Driver has zero video reachability, unconditionally — out of ADR-0026's own scope.
2. **RAAD is not a video archive.** This service stores no video; the MDVR is the sole system of
   record. Only ephemeral session/port/token state (Redis) and control metadata (`video_sessions`,
   `playback_requests` in the Business DB) are persisted.
3. **Device signaling is not this service's job.** The Business API signals the physical device via
   JT808 command downlink (0x9101 live, 0x9201/0x9205/0x9202 playback, 0x9102 stop); this service
   only receives and repackages the resulting media stream.
4. **Concurrency is bounded.** Enforce a per-org and global max-concurrent-stream ceiling; requests
   beyond the ceiling are refused with a clear message (`SessionCapacityExceededError`). Ports are
   pooled and reclaimed on teardown.
5. **Media is repackaged, never passed through raw.** JT1078 frames become WebRTC (primary,
   low-latency) or HLS/FLV (fallback); clients never speak JT1078 directly. The mobile player
   (`mobile/lib/features/video/`, ADR-0026 §5) consumes WS-FLV specifically — HLS/WebRTC remain
   future work, unbuilt.
6. **Every session open/close is audited**, with actor, device, camera, and time — implemented at
   the `VideoSession` level via the shared `audit_entries` architecture (ADR-0007); viewer-level
   join/leave is not separately audited.
