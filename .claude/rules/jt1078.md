# Rule: JT1078

Derived from `docs/business/RAAD_Phase3.5_JT1078_Technical_Design_v1.md`.

**Status (ADR-0009, ADR-0024, ADR-0025):** the procured hardware (`LSZ-C5804DG-Q-F`) is confirmed
JT/T 1078-2016 compliant (ADR-0025, 2026-08-10, superseding ADR-0009's original non-compliance
finding for this hardware). Rule #3's "JT808 command downlink" is literal, not illustrative:
`0x9101`/`0x9102`/`0x9201`/`0x9202`/`0x9205` are standard JT/T 808-enveloped messages, forwarded
by `device-gateway`'s `vendors/jt808/` adapter on the connection it already holds — no
vendor-specific opcode translation, **implemented 2026-08-11** (`commands/video_signaling.py` +
`commands/redis_video_signaling_consumer.py`).

**`services/jt1078/` itself is now a real, tested relay (2026-08-11), not the empty scaffold this
status paragraph originally described** — JT/T 1078 extended-RTP ingest + subpackage reassembly
(spec-verified), session lifecycle, signed single-use viewer tokens, FLV repackaging, and a
hand-rolled WS-FLV viewer server, all unit/integration-tested over real loopback sockets with
synthetic frames, never against the physical MDVR. Rules #1/#2/#5 below are implemented as
described. **Rule #4's concurrency ceiling is only partially implemented**: per-device mutual
exclusivity holds structurally (one session resolves per `terminal_id` at a time), but no
per-org/global max-concurrent-stream *ceiling* is enforced yet — a real, disclosed gap, not
silently assumed done. **Rule #6's audit requirement is not yet implemented** — this relay
publishes session-lifecycle events onto the broker, but writing them into the shared
`audit_entries` architecture (ADR-0007) is a Business-API-side responsibility, and no Business-API
adapter consumes these events for that purpose yet (out of this phase's scope, deliberately — see
this session's own report).

**Business API `VideoProviderPort` → relay wiring is now real (2026-08-12)** — closes the
"no Business-API-facing control endpoint" gap this status paragraph and `services/jt1078/
README.md`'s own "Explicitly not built this phase" list both previously named.
`backend/raad/modules/video/infra/adapters.Jt1078RelayAdapter` calls a new
`Jt1078RelayRpcClient` (`backend/raad/modules/video/infra/jt1078_relay_client.py`) — a Redis
list-based BLPOP/RPUSH RPC (`raad:jt1078:session_requests` /
`raad:jt1078:session_responses:{request_id}`) — answered by a new `SessionRequestServer`
(`services/jt1078/src/session/session_request_server.py`), then publishes
`Jt1078SignalCommandRequested` on the **existing** broker stream exactly as ADR-0024 §8 already
specifies for device-gateway. **This RPC channel is new and additive, not a replacement for
ADR-0024 §8's mechanism**: device-gateway ↔ relay coordination stays broker-only, unchanged; the
RPC exists solely for the backend ↔ relay session-request/response shape, which the broker's
fan-out Stream model doesn't fit. Full flow: `VideoApplicationService` → `Jt1078RelayAdapter` →
RPC → `SessionRequestServer` (allocates ingest coordinates, mints the viewer token) → broker event
→ device-gateway's `RedisVideoSignalingConsumer` (already built) → real `0x9101`/`0x9201` on the
device's connection.

**One disclosed, deliberate refinement of ADR-0024 §5 point 2's literal wording**: that section
reads "a... signed viewer token minted by the backend at session-creation time." In the
implementation, the **relay** mints the token — the backend never holds
`JT1078_RELAY_VIEWER_TOKEN_SECRET` (relay-only config, by design, so a compromised backend process
still can't forge a token for a session it never legitimately brokered). The security property
ADR-0024 §5 actually protects — no session-authorization decision happens outside the backend's
own D5/RBAC check, which runs before the RPC call is ever made — is unchanged; only which process
computes the token's bytes differs from the section's literal phrasing.

**One real, disclosed gap this wiring does not close**: `backend/raad/modules/video/events/
subscribers.py` is still empty — the relay's own session-lifecycle events (`VideoSessionActivated`/
`Ended`/`Failed`, published today) are not yet consumed back into `VideoSession`. `VideoSession`
transitions to `ACTIVE` as soon as the RPC call + device signal succeed, not on a real
"media is actually flowing" signal from the relay (ADR-0024 §5 point 3); an automatic,
relay-initiated teardown (idle timeout, viewer disconnect, device drop) has no path back into
Postgres today, and ADR-0024 §16's own "defensive timeout on any `VideoSession` stuck in
`REQUESTED`/`ACTIVE`" reconciliation safety net does not exist yet either — a pre-existing
simplification in the `video` module's control flow, not something this phase introduced, but
directly relevant to how far this integration should be trusted and therefore recorded here.

1. **Parents have zero reachable path to video, anywhere, ever.** This is a platform-wide invariant
   (D5), not a configurable setting. Authorization is enforced in the Business API before any
   signaling reaches this service.
2. **RAAD is not a video archive.** This service stores no video; the MDVR is the sole system of
   record. Only ephemeral session/port/token state (Redis) and control metadata (`video_sessions`,
   `playback_requests` in the Business DB) are persisted.
3. **Device signaling is not this service's job.** The Business API signals the physical device via
   JT808 command downlink (0x9101 live, 0x9201/0x9205/0x9202 playback, 0x9102 stop); this service
   only receives and repackages the resulting media stream.
4. **Concurrency is bounded.** Enforce a per-org and global max-concurrent-stream ceiling; requests
   beyond the ceiling queue or are refused with a clear message. Ports are pooled and reclaimed on
   teardown.
5. **Media is repackaged, never passed through raw.** JT1078 frames become WebRTC (primary,
   low-latency) or HLS/FLV (fallback); clients never speak JT1078 directly.
6. **Every session open/close is audited**, with actor, device, camera, and time.
