# Rule: JT808

Derived from `docs/business/RAAD_Phase3.4_JT808_Technical_Design_v1.md`.

**Reality check (ADR-0009, ADR-0010):** this rule file describes RAAD's target device-plane
architecture for a genuinely JT/T 808-compliant vendor. The first procured hardware (Shenzhen
Tianyou / "LSZ", `LSZ-C5804DG-Q-F`) is **not** JT/T 808-compliant — see `docs/vendor/
HARDWARE_ANALYSIS.md` §2 and `docs/architecture/adr/0009-mdvr-vendor-protocol-device-plane.md`.
That hardware is served by a parallel protocol stack, `services/device-gateway/src/vendors/lsz/`
(the device-plane deployable itself renamed `services/jt808/` → `services/device-gateway/` and
reorganized into `src/vendors/<name>/` per ADR-0010, once it grew a second vendor adapter — the
original JT/T 808 code now lives at `src/vendors/jt808/`, moved verbatim), which follows rule #2
below at a full-protocol-swap grain rather than a within-JT/T-808 dialect variation, and rule #4/#5
in a necessarily reduced form (this vendor's protocol has no cryptographic auth mechanism at all —
network-layer compensating controls substitute, per `.claude/rules/security.md` #9; a broker-driven
device-registry projection, ADR-0010, is the real, non-interim provisioning source). Rules #1, #3,
#6, #7 apply identically regardless of which protocol stack is active — the event contract and
architectural boundary do not change with the wire protocol; `DeviceOnline`/`DeviceOffline`/
`DeviceAlarmRaised`/`DevicePositionReported` are now all real, Redis-published events (ADR-0010),
not just named log lines.

1. **This service never writes Business API tables directly.** It only publishes domain events
   (`DevicePositionReported`, `DeviceOnline`, `DeviceOffline`, `DeviceAlarmRaised`, command-result
   events) to the broker.
2. **Vendor dialect variation is isolated in an Anti-Corruption Layer.** A new vendor means a new
   adapter — never a change to the core parser/dispatcher/handlers.
3. **Backfilled data is flagged and time-honest.** Buffered positions (0x0704, late 0x0200) publish
   with their original timestamp and `backfill=true`; live views must only use `event_time ≈ now` so
   stale buffered data never corrupts the live map.
4. **Session state lives in Redis**, keyed by `device_id -> {node, vehicle_id, org_id, last_seen,
   auth_state}` — the shared source of truth enabling sharded, sticky device connections.
5. **Unknown/unauthenticated devices are rejected and audited**, never silently dropped without a
   trace.
6. **Command downlink is correlation-ID tracked** — every platform-issued command (0x9101, 0x9201/
   0x9205, 0x8300, 0x8103, 0x8105) must be traceable back to the requesting use-case and its result.
7. **Connectivity monitoring is heartbeat-driven.** Timeout emits `DeviceOffline`; reconnect emits
   `DeviceOnline` — these feed device-status monitoring and exception workflows directly.
